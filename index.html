Turnero Exiauto

2. Roles y pantallas

El sistema tiene 5 roles. Cada usuario entra a su pantalla automáticamente tras el login.

Vigilancia (Garita)
/garita/
  • Ve turnos pendientes que llegaron por QR
  • Confirma o rechaza cada vehículo
  • Registra vehículos manualmente
  • Ve la cola activa en tiempo real
Asesor
/asesor/
  • Llama al siguiente turno en su módulo
  • Ve el turno en atención
  • Finaliza, re-llama o devuelve a la cola
  • Ve la cola completa en tiempo real
Supervisor
/en-vivo/
  • Vista general de todos los módulos
  • Accede a reportes y exportación Excel
  • Configura parámetros del sistema
  • Gestiona horario del taller
Admin
/en-vivo/ + /admin/
  • Todo lo del Supervisor
  • Crea y gestiona usuarios
  • Genera tokens para pantallas TV
  • Acceso al admin Django completo
TV (Sala de Espera)
/tv/?token=…
  • No requiere login
  • Muestra turnos llamados en tiempo real
  • Reproduce sonido al llamar (opcional)
  • Acceso por token de dispositivo
ℹ️
TV Sala de Espera: Para instalar en un televisor, abre el navegador del TV en la URL completa con el token. El token está en /admin/ → DeviceTokens. Se puede generar uno nuevo por cada televisor.

3. Flujo de trabajo diario

Entrada del cliente (dos formas)

A) Cliente escanea QR (self-service)
  • El cliente apunta su teléfono al código QR del taller (/turnos/qr-checkin.png)
  • Llena su placa y nombre en el formulario /checkin/
  • Recibe un número de turno y un enlace de seguimiento personalizado
  • El turno queda en estado Pendiente hasta que Vigilancia lo confirme
B) Vigilancia registra manualmente (en garita)
  • El guardia ingresa la placa desde /garita/
  • El turno queda directamente en En espera (sin paso de confirmación)

Estados de un turno

PENDIENTE → EN_ESPERA → LLAMADO → EN_ATENCIÓN → FINALIZADO (QR) (confirmado) (asesor) (atendiendo) │ └──────────────────────────────────────→ RECHAZADO └──────────────────────────────────────────────────────→ RECHAZADO └→ NO_SE_PRESENTÓ └→ EN_ESPERA (devuelve a cola)

Los turnos que llevan más de 30 minutos en Pendiente son marcados automáticamente como Vencido por el sistema (cron job cada 5 minutos).

Prioridad de la cola

Los turnos Con cita tienen prioridad sobre los walk-ins (Sin cita). Dentro de cada categoría, se atiende por orden de llegada.

4. Correr el proyecto en local (Docker Compose)

ℹ️
Necesitas: Docker Desktop (Windows/Mac) o Docker + Docker Compose (Linux). No se necesita Python, PostgreSQL ni Redis instalados por separado.
  1. Descomprime el código fuente

    Extrae el archivo turnero-exiauto-codigo.zip en la carpeta que prefieras.

  2. Crea el archivo de variables de entorno

    Dentro de la carpeta backend/, crea un archivo llamado .env con este contenido:

    SECRET_KEY=cambia-esto-por-una-clave-secreta-larga-aleatoria
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1
DATABASE_URL=postgresql://exiauto:exiauto@db:5432/turnero_exiauto
REDIS_URL=redis://redis:6379/0
DJANGO_SUPERUSER_USERNAME=admin
DJANGO_SUPERUSER_PASSWORD=admin123
DJANGO_SUPERUSER_EMAIL=admin@exiauto.com
  3. Levanta la base de datos y Redis

    Desde la carpeta backend/ ejecuta:

    docker compose up -d db redis

    Espera ~5 segundos a que PostgreSQL esté listo (el healthcheck lo verifica automáticamente).

  4. Aplica migraciones y carga datos de prueba 
    docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py cargar_datos_prueba

    Esto crea los usuarios, módulos y turnos de prueba automáticamente.

  5. Levanta el servidor 
    docker compose up web

    El servidor queda en: http://localhost:8000

✅
Listo. Las mismas credenciales de producción funcionan en local: admin/admin123, luisa/pass123, vigilancia/pass123, etc.

Correr sin Docker (Python directo)

Si prefieres correr sin Docker, necesitas Python 3.11+, PostgreSQL y Redis instalados localmente. Luego:

cd backend
python -m venv .venv && source .venv/bin/activate   # En Windows: .venv\Scripts\activate
pip install -r requirements.txt
# Copia y edita el .env con los datos de tu base de datos local
python manage.py migrate
python manage.py cargar_datos_prueba
daphne -b 0.0.0.0 -p 8000 config.asgi:application

Correr los tests

cd backend
pytest   # 124 pruebas, 0 fallos

5. Deploy en Railway

El sistema está configurado para desplegarse automáticamente en Railway. Cada git push a la rama master dispara un nuevo deploy.

Servicios requeridos en Railway

Servicio 1: Web (aplicación Django)
  • Build: Dockerfile en la carpeta backend/
  • Puerto: 8000 (Railway lo asigna automáticamente en $PORT)
  • Al iniciar, corre automáticamente: migrate → collectstatic → createsuperuser → cargar_datos_prueba → daphne
Servicio 2: PostgreSQL
  • Añadir desde Railway → "New" → "Database" → PostgreSQL
  • Railway inyecta DATABASE_URL automáticamente
Servicio 3: Redis
  • Añadir desde Railway → "New" → "Database" → Redis
  • Railway inyecta REDIS_URL automáticamente
Servicio 4: Cron Job (vencer turnos expirados)
  • Desde Railway → "New" → "Cron Service"
  • Schedulo: */5 * * * * (cada 5 minutos)
  • Comando: python manage.py vencer_pendientes
  • Mismo Dockerfile, mismas variables de entorno
